## Store ZIP policy

`Asterfold-Chrome.zip` is generated from the production MV3 runtime directory before unpacked-install documentation is added. The package validator requires `manifest.json` at the root and rejects source maps, environment files, docs, tests, Store screenshots, nested archives, traversal, duplicate entries, symlinks, unexpected executable files, remote code patterns and secrets.

Runtime policy confirmed by production E2E and manifest validation:

- Version: `3.0.1`
- Manifest version: 3
- Permissions: `activeTab`, `favicon`, `alarms`, `contextMenus`, `storage`
- Optional permission: `bookmarks`
- Host permissions: none
- Content scripts: none
- Remote executable code: none
- Strict extension CSP: enabled

## Tag and release automation

After PR merge, the exact final `main` SHA must pass CI and CodeQL. A main-only workflow then verifies the public Privacy Policy unauthenticated with desktop and mobile user agents, confirms version 3.0.1 and Limited Use text, checks tag/release conflicts, and creates annotated tag `v3.0.1` on that exact main SHA.

The tag-triggered release workflow must publish:

- `Asterfold-Chrome.zip`
- `chrome-unpacked.zip`
- `extension-source.zip`
- `Asterfold-Store-Assets.zip`
- `checksums.txt`
- `provenance.json`
- `sbom.spdx.json`

It must then download the published assets, verify checksums, provenance and GitHub artifact attestations, and compare the downloaded Store ZIP with the tested release subject.
